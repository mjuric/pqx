# pqx in Go: the full port

Status: **plan approved by the owner 2026-10-08**; wave 0 in progress. Background, measurements and the prototype's results are in
[native-port.md](native-port.md); the prototype's plan is in
[go-prototype.md](go-prototype.md).

## Context

The prototype on `native-port` showed that a Go pqx starts 10–14× sooner than
Python pqx (0.15–0.3 s against 1.8–2.6 s), pages and jumps 2–4× faster, and
cancels sooner. The owner's goals are speed and an install without Python;
DuckDB stays as the query engine.

The full port brings the Go version to parity with Python pqx 0.2.0, as the
README and the `?` help describe it, then replaces the Python package on PyPI
under the same name. Python pqx 0.2.0 final ships first, from `master`, before
2026-10-19; the port does not touch `master` until the owner approves the
cutover.

Size of the job: Python pqx is about 7,100 lines (`app.py` 3,250, `data.py`
1,520, `fmt.py` 450, `plots.py` 450, `screens.py` 390, `cells.py` 280,
`widgets.py` 250, the rest small) plus a 400-line stylesheet, with 221 tests.
About 115 tests are pure logic and port as Go table tests; about 104 drive the
UI through Textual's pilot and have to be rewritten as Bubble Tea model tests;
16 test Textual internals and are dropped. The prototype has about 3,200 lines
and 50 tests; its grid, paging, `g`, plain and filtered reads, counts,
cancellation, `Sanitize` and filter checks are done.

## Approach

### Package layout

```
go/
  cmd/pqx/              CLI: options, env vars, --version, -h; starts the app
  internal/data/        the dataset (contract in data.go)
  internal/fmtx/        port of fmt.py: kinds, value formatting, overrides,
                        Python format specs, derived readings, sanitize
  internal/cells/       cell widths (East Asian width, combining), widest candidates
  internal/plots/       histogram, density map, Mollweide sky map, colormaps
  internal/config/      formats.yaml, same file format and locking as config.py
  internal/term/        input filter (split X10/urxvt mouse, lenient UTF-8),
                        clipboard, clear-on-exit
  internal/ui/          the Bubble Tea app
    app.go              root model: layout, focus, tabs, dialog stack, Esc ladder
    tasks.go            background jobs: tags, supersede, cancel, user vs own work
    grid/ filter/ detail/ schema/ meta/ stats/ plot/ dialogs/ status/
  internal/theme/       styles: terminal palette, accent, dim, border, named themes
  testdata/golden/      golden files from Python pqx (generated, checked in)
  bench/                pty harness, parity scenarios, benchmarks
```

### The contract (written by the integrator before any WP starts)

The prototype's `Window` holds formatted strings, so the UI never sees values.
Smart formatting, `=`, copy, digits and the details pane all need the raw value.
The contract changes that:

- **Values.** `Window.Cols` becomes `map[string][]Value`, where `Value` is `any`
  holding one of: `nil`, `int64`, `uint64`, `float64`, `float32`, `bool`,
  `string`, `[]byte`, `time.Time` (UTC), `Date`, `Duration`, `Decimal`
  (`*big.Int` plus scale, so wide decimals stay exact), `UUID`, `[]Value`,
  `Struct` (ordered fields) and `Map`. Both readers (arrow-go and DuckDB)
  produce the same `Value` for the same cell; a test checks that over a zoo of
  types, as `test_fetch.py` does for PyArrow and DuckDB.
- **Columns.** `Column` gains `ArrowType`, `Nullable`, `Unit`, `Description`
  (field metadata, felis `"[unit] desc"`), `SQLName` (DuckDB's name for
  case duplicates). The formatting kind comes from `fmtx`, not the data layer.
- **Views.** `View{Where, OrderBy, Desc, SQL}`. A SQL view has its own result
  columns and no file rows.
- **Dataset methods** (all reading calls take a `ctx` and stop on cancel):
  `Fetch`, `FetchColumns(fileRows, cols)`, `Count`, `Validate(view)`
  (returns the result columns), `FindRow`, `FetchAround`, `ColumnStats`,
  `Histogram`, `SkyCounts`, `XYCounts`, `Export`, `FooterSummary` (per-column
  nulls, min/max, sizes, ratio), `RowGroupInfo`, `Encodings`, `KeyValueMetadata`,
  `FileInfo`; with `Sample` options for stats and plots.
- **fmtx API**: `KindFor(name, type, unit)`, `Format(v, kind, Opts{Raw, Width,
  Override})`, `Derived`, `StepOverride`, `OverrideError`, `Sanitize`,
  `HumanCount`, `HumanBytes`, `Percent`, `ShortType`.
- **UI skeleton**: the root model, the interfaces each pane and dialog
  implements (`Update`, `View(w, h)`, `Keys()` for the key bar, `Focusable`),
  message types, the task registry, notifications (toasts), and the key-bar
  and status-line plumbing. Each UI WP fills its own package.

WPs code against the contract and must not change it; a needed change comes
back to the integrator, who applies it and tells the agents it affects.

### Things to carry over exactly

From the inventory of `app.py` (and in native-port.md): the viewport and
record keeping across `=`, sort, clear and hide; keys queued while the record is
looked up; the Esc ladder (close the pane unless user work runs; cancel
everything when busy; leave inputs); lazy columns with reserved widths from
row-group statistics, so the grid doesn't shift; columns that only grow and
are never shown cut off; failed columns shown as ✗ and not retried; the status
line priorities; all file text through `Sanitize`, never interpreted as
markup; filters checked as one SELECT with balanced parentheses; glob escaping;
UTC; `formats.yaml` compatible both ways; the title bar dropping the version
first; the filter hint from the file's first row.

Known gaps from the prototype that the port closes: wide decimals (exact
`Decimal`), a DuckDB fallback for columns arrow-go can't read, backslashes next
to glob characters, the split X10 mouse report, emoji and CJK widths, and a
blocking table function leaving a connection behind (bounded by closing the
connection on cancel).

### Performance targets

Measured with the pty harness, warm cache, 200×50, against the prototype's
numbers; a regression of more than 20% is a bug:

- first screen: SSSource ≤ 0.25 s, 2,000 row groups ≤ 0.4 s;
- PgDn ≤ 50 ms, `g` to the middle and Ctrl+End ≤ 150 ms on all four bench files;
- Esc until "cancelled" ≤ 100 ms;
- a frame on a 300-column screen ≤ 5 ms.

## Validation

- **Unit and golden tests** for `data`, `fmtx`, `cells`, `plots`, `config`,
  `term`: the pure-logic Python tests ported case by case, plus golden files
  from Python pqx (D7a).
- **Model tests** for the UI: the 104 pilot tests re-expressed as Bubble Tea
  `Update`/`View` tests against a fake dataset and against the fixtures; each
  Python test file maps to a WP below.
- **Pty parity harness** (WP5, black box): about 40 key scripts covering the
  README tour, every key in the help, the security cases (a file whose strings
  hold escape sequences must never reach the terminal raw), and the record- and
  viewport-keeping cases; run on Python and Go, screens compared after
  normalizing the version and timings.
- **Real data, end to end**: SSSource, mpc_orbits, SSObject, the wide and
  many-row-group files; every tab, a filter, a SQL query, `=`, sort, export (to
  the scratchpad), stats and a sky map.
- **Platforms**: CI on Linux and macOS; a release-candidate wheel installed with
  `pip` and `uvx` on each platform; a check by the owner in iTerm2 over ssh and
  in GNU screen.

## Implementation plan

Waves follow the dependencies. Each WP is built by a subagent in its own
worktree on a branch from `native-port`, and merges through its own PR (merge
commit) after review and the full test suite. **Independent review** (a fresh
agent that tries to break it) for WPs marked ★; a light review for the others.

### Wave 0: the integrator

- **W0.1 Contract**: `data.go`, `fmtx` and `plots` signatures, the `Value`
  types, the UI skeleton (root model, interfaces, task registry, messages).
  The prototype's data layer and grid are moved onto it so everything compiles
  and the existing tests pass.
- **W0.2 Fixtures and golden files**: Go writers for the `demo`, `odd` and
  hostile fixtures; a Python script (`go/testdata/golden/make_golden.py`) that
  runs Python pqx's `fmt`, `cells`, `plots` and `data` on them and writes
  JSON; `testdata/README.md` with the facts about each fixture.
- **W0.3 CI**: `go.yml` on Linux and macOS, `gofmt`, `vet`, tests,
  `staticcheck`.

### Rules for the agents

- Start with `git fetch && git reset --hard origin/native-port`; work only in
  `go/` (WP13 also in `.github/` and `docs/`); never change the contract.
- Go 1.27 at `/root/sdk/go/bin`; `make` sets the `duckdb_arrow` tag; `gofmt`,
  `go vet` and `go test ./...` pass before each commit.
- Tests use the fixtures and `t.TempDir()`; the real files are read-only;
  large generated files go in the scratchpad and are deleted after use.
- DuckDB threads in tests at most 8; at most 32 cores per agent.
- Commit with the attribution trailers; push the branch and open the PR into
  `native-port`; report what was done, what was skipped and any contract change
  needed.
- Plain, specific wording in code, commits and PRs.

## Risks

- **Python format specs and strftime** (`F`, `--format`, `formats.yaml`) have
  no Go equivalent; WP3 writes a mini-language parser for the subset pqx
  validates, with the golden files as the check.
- **Textual layout behaviour** (dialogs over the screen, border titles, focus)
  is rebuilt by hand in Lip Gloss; the parity harness is what catches drift.
- **The record-keeping logic** (`app.py` 1578–1701 and `_set_view`) is the
  subtlest part of the app; WP11 gets the longest review.
- **Binary size** is about 90 MB, 31 MB compressed; acceptable for wheels
  (PyPI's per-file limit is 100 MB by default).
